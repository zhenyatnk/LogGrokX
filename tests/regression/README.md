# Регрессионный набор LogGrokX для AI-агента

Набор ручных (UI) регресс-кейсов для проверки LogGrokX перед релизом. Его выполняет AI-агент,
который управляет Windows-десктопом (мышь, клавиатура, скриншоты, PowerShell). Каждый тест-кейс
лежит в отдельном файле `cases/<ID>.md`, имя файла совпадает с идентификатором кейса.

| Что | Где |
|---|---|
| Тест-кейсы | [`cases/`](cases/) — `RT-<ОБЛАСТЬ>-<NNN>.md` |
| Матрица покрытия (требования → кейсы, дефекты → кейсы) | [`COVERAGE.md`](COVERAGE.md) |
| Тестовые данные | [`testdata/`](testdata/) |
| Конфигурации для тестов | [`testdata/config/`](testdata/config/) |
| Утилиты (PowerShell) и генераторы (Python) | [`tools/`](tools/) |
| Отчёты прогонов | `reports/<YYYY-MM-DD_HHMM>_<версия>/` (создаёт агент) |

Кейсы и `COVERAGE.md` генерируются из `tools/casedata/*.py` скриптом `tools/generate_cases.py`.
Скрипт проверяет, что каждое требование и каждый закрытый дефект покрыты хотя бы одним кейсом,
что ID уникальны, а у шагов есть ожидаемый результат. Если сломать покрытие, генерация упадёт.
Править нужно `casedata`, а не сгенерированные `.md`.

```powershell
python tests\regression\tools\generate_cases.py          # перегенерировать cases/ и COVERAGE.md
python tests\regression\tools\generate_cases.py --check  # только проверить покрытие
python tests\regression\tools\generate_testdata.py       # перегенерировать testdata/ (нужен пакет cryptography)
```

## Запуск тестирования

Агенту передаётся промпт ниже. Перед отправкой нужно заменить значения в угловых скобках.
Строку «Состав прогона» можно взять из вариантов под промптом.

```text
Ты — тестировщик LogGrokX. Выполни регресс-тестирование по набору tests/regression.

Входные данные:
- Рабочая копия репозитория: <C:\src\LogGrokX>
- Тестируемая сборка: <C:\LogGrokX\LogGrokX.exe>, вид сборки: <setup | portable | self-contained | локальная>
- Состав прогона: <все кейсы из tests/regression/cases>
- Доступно: сеть <да/нет>, права администратора <да/нет>,
  предыдущая версия для обновления <путь к установщику или «нет»>

Порядок работы:
1. Прочитай tests/regression/README.md целиком и строго следуй разделам «Окружение»,
   «Подготовка окружения», «Правила выполнения для агента» и «Формат отчёта».
2. Вычисли значения %RT%, %APP%, %DATA%, %LOGS%, %TEMP% и запиши их в отчёт.
3. Сделай резервную копию пользовательского состояния и выполни подготовку окружения.
4. Выполняй кейсы в порядке P1 → P2 → P3, внутри приоритета — по ID. Кейсы RT-UPD-* и
   RT-INS-* выполняй последними. Перед каждым кейсом читай его файл cases/<ID>.md полностью.
5. Проверяй каждый ожидаемый результат буквально. Сохраняй доказательства в
   artifacts/<ID>/: скриншоты шагов, содержимое буфера обмена, вывод PowerShell.
6. Если нет внешнего ресурса или прав, ставь BLOCKED с причиной и не пытайся обойти
   ограничение. Если кейс просит зафиксировать фактическое поведение, опиши, что увидел.
7. При падении или зависании приложения собери данные по правилу «Аварии», перезапусти
   приложение и продолжи со следующего кейса.
8. После прогона восстанови резервную копию пользовательского состояния.

Ограничения:
- Не меняй код продукта, тестовые данные и кейсы.
- Не создавай issue и не отправляй ничего в GitHub.
- Не выполняй действий вне тестового стенда.

Результат:
- Каталог tests/regression/reports/<YYYY-MM-DD_HHMM>_<версия>/ с report.md, results.json
  и artifacts/ строго по формату из README.
- В конце ответа кратко: вердикт (READY / READY_WITH_REMARKS / NOT_READY), число кейсов
  по статусам, список дефектов S1–S2 с ID кейсов.
```

Варианты строки «Состав прогона»:

| Цель | Значение |
|---|---|
| Полный регресс перед релизом | `все кейсы из tests/regression/cases` |
| Быстрая проверка | `только кейсы с приоритетом P1` |
| Проверка доработки | `кейсы областей SRCH, SAV` или явный список ID, например `RT-JSN-001, RT-JSN-004` |
| Проверка исправленного дефекта | `кейсы, связанные с issue #89, по COVERAGE.md` |
| Стенд без сети и прав администратора | `все кейсы, кроме RT-UPD-*, RT-INS-001, RT-DMP-001, RT-STK-002, RT-STK-003` (это кейсы с отметкой «Внешние ресурсы / ручные действия: Да»; в RT-SUP-001 сетевые шаги получат BLOCKED) |

## Идентификаторы и структура кейса

- ID: `RT-<ОБЛАСТЬ>-<NNN>`, например `RT-SRCH-002`. Перечень областей и их кодов — в [`COVERAGE.md`](COVERAGE.md#области).
- Требования: `REQ-<ОБЛАСТЬ>-<NN>`. Это атомарные утверждения о поведении продукта, собранные по
  `README.md`, `FEATURES.md`, коду и закрытым issue. Набор считается полным, если каждое
  требование покрыто хотя бы одним кейсом. Сейчас покрытие 100%, его проверяет генератор.
- Приоритеты:
  - `P1` — критичная функциональность, без неё релиз блокируется;
  - `P2` — важная функциональность;
  - `P3` — второстепенная функциональность или функциональность, которой нужны особые условия.
- Типы: `Функциональный`, `Краевой`, `Негативный`, `Регрессия дефекта` (всегда со ссылкой на
  issue), `Нефункциональный` (производительность, память, отзывчивость).
- Разделы кейса:
  - шапка: ID, область, приоритет, тип, требования, профиль, конфигурация, данные, длительность,
    дефекты, нужны ли внешние ресурсы;
  - Цель;
  - Проверяемые требования;
  - Предусловия;
  - Шаги — таблица «№ | Действие | Ожидаемый результат»;
  - Критерии прохождения;
  - Краевые случаи и примечания;
  - Артефакты для отчёта;
  - Очистка.

## Окружение

| Требование | Значение |
|---|---|
| ОС | Windows 10 22H2 или Windows 11 (x64). Для кейсов x86 — 32-разрядная сборка. Разрешение экрана не ниже 1920×1080, масштаб 100% (иначе указать масштаб в отчёте). |
| Тестируемая сборка | Релиз с [GitHub Releases](https://github.com/zhenyatnk/LogGrokX/releases): setup, portable или self-contained zip. Либо локальная сборка `dotnet build LogGrokX.sln -c Release` (у неё версия `0.0`, это нужно указать в отчёте). |
| PowerShell | PowerShell 7+ (`pwsh`) для утилит из `tools/`. |
| Python | Python 3.10+ и `pip install cryptography`. Нужен только для перегенерации данных. Готовые данные уже лежат в репозитории. |
| Сеть | Доступ к `github.com` (кейсы `UPD`, `SUP`) и `msdl.microsoft.com` (`RT-STK-002`). Если доступа нет, кейс получает статус `BLOCKED`. |
| Права | Обычный пользователь. Для `RT-DMP-001` и `RT-INS-001` (установка для всех пользователей) нужен администратор с UAC. |

### Переменные путей

В кейсах используются условные переменные. Перед стартом агент вычисляет их значения и записывает
в отчёт.

| Переменная | Значение |
|---|---|
| `%RT%` | Абсолютный путь к `tests\regression` в рабочей копии репозитория. |
| `%APP%` | Папка, где лежит тестируемый `LogGrokX.exe` (рядом лежит `appsettings.yaml`). |
| `%DATA%` | `%LOCALAPPDATA%\LogGrokX\Data`: тема, сохранённые поиски, кэш автодополнения, состояние обновлений. |
| `%LOGS%` | `%LOCALAPPDATA%\LogGrokX\`: диагностические логи приложения. |
| `%TEMP%` | Временная папка пользователя. Сюда пишутся большие и сгенерированные файлы. |

## Подготовка окружения

Подготовку выполняют один раз перед прогоном. Шаги 3–5 повторяют перед каждым кейсом, который
меняет конфигурацию или данные пользователя (это указано в разделе «Очистка» кейса).

1. Закрыть все экземпляры LogGrokX: `Get-Process LogGrokX -ErrorAction SilentlyContinue | Stop-Process`.
2. Сделать резервную копию пользовательского состояния в `%TEMP%\lgx-backup\`:
   - `%APP%\appsettings.yaml`;
   - из `%DATA%`: `Theme.json`, `SavedSearches.json`, `AutocompleteCache.json`,
     `last-update-check.settings`, `skipped-update.settings`, `available-update.json`,
     `pending-update.json`, `update-restart.json`.
3. Скопировать `%RT%\testdata\config\appsettings.regression.yaml` в `%APP%\appsettings.yaml`. Это
   поставляемые профили `Classic`, `Venn`, `Plain text` плюс тестовый профиль `Regression`,
   `Language: en`, `UpdateMode: disabled`, `BigLine: prune`, `BigLineSize: 4096`.
4. Удалить перечисленные выше файлы из `%DATA%`, чтобы прогон начинался с чистого состояния
   (светлая тема, нет сохранённых поисков и истории).
5. Запустить `%APP%\LogGrokX.exe` и убедиться, что выбран профиль `Classic`, тема светлая, а
   интерфейс на английском. Ожидаемые тексты в кейсах приведены для английского интерфейса.
6. Проверить, что тестовые данные на месте: `Get-ChildItem %RT%\testdata -Recurse | Measure-Object`.
   Если данные перегенерировались, сверять значения сертификата с `testdata\binary\EXPECTED.md`:
   thumbprint меняется при каждой генерации.
7. Записать в отчёт версию (`& "%APP%\LogGrokX.exe" --version`), commit и branch из окна Support,
   версию ОС, архитектуру и вид сборки (setup / portable / self-contained / локальная).

После прогона восстановить резервную копию из `%TEMP%\lgx-backup\`.

## Правила выполнения для агента

1. **Порядок.** Сначала все `P1`, затем `P2`, затем `P3`. Внутри приоритета кейсы идут по ID.
   Кейсы `RT-UPD-*` и `RT-INS-*` меняют установленную версию, поэтому их выполняют последними
   (желательно на отдельной виртуальной машине).
2. **Независимость.** Каждый кейс начинается из базового состояния: подготовка выполнена,
   документы закрыты, профиль `Classic`. Нельзя опираться на состояние, оставленное предыдущим
   кейсом, если в предусловиях явно не сказано обратное (например, `RT-VM-002` использует списки
   из `RT-VM-001`). После кейса выполнить раздел «Очистка».
3. **Строгость сравнения.** Ожидаемый результат проверяется буквально: тексты сообщений, числа,
   порядок строк, ID записей (`[S10]`, `[T04]` и т. п.). Если ожидание сформулировано через
   «или» либо «зафиксировать фактическое поведение», агент описывает, что увидел, и ставит
   `PASS`, если наблюдение укладывается в допустимые варианты.
4. **Доказательства.** На каждом шаге с проверкой UI агент делает скриншот
   `artifacts/<ID>/step-NN.png`. Буфер обмена проверяется через `Get-Clipboard -Raw`, и
   результат (или его первые и последние 500 символов и длина) сохраняется в
   `artifacts/<ID>/clipboard-NN.txt`. Файлы и реестр проверяются командами PowerShell, вывод
   сохраняется в отчёт.
5. **Время.** Если в кейсе есть порог («≤ 2 с»), время измеряется по секундомеру или
   `Measure-Command` и записывается в отчёт. Если порога нет, UI не должен зависать дольше 5 с.
   Общий тайм-аут кейса — три ориентировочные длительности. После него кейс получает статус
   `FAIL` с пометкой `timeout`.
6. **Нестабильность.** Если шаг провалился из-за, вероятно, временной причины (не успела
   отрисоваться анимация, окно не получило фокус), агент повторяет шаг один раз. Если повтор
   прошёл, ставится `PASS` с пометкой `flaky` и описанием. Если нет — `FAIL`.
7. **Аварии.** Если приложение упало или зависло (не отвечает дольше 30 с):
   - снять скриншот;
   - сохранить последние 200 строк самого свежего лога из `%LOGS%` и дамп, если дампы включены;
   - записать события `Application` из журнала Windows за последние 10 минут
     (`Get-WinEvent -FilterHashtable @{LogName='Application'; StartTime=(Get-Date).AddMinutes(-10)}`);
   - перезапустить приложение и перейти к следующему кейсу.
   Кейс получает статус `FAIL` и серьёзность `S1`.
8. **Ограничения.** Не менять код продукта, тестовые данные и кейсы во время прогона. Не
   отправлять отчёты об ошибках в GitHub автоматически. Не выполнять действия вне тестового
   стенда: не трогать чужие файлы и не устанавливать постороннее ПО.
9. **BLOCKED.** Ставится, если нет внешнего ресурса (сети, прав администратора, предыдущей
   версии для обновления, PDB) или не выполнено предусловие не по вине продукта. Причину нужно
   указать обязательно. Кейсы с отметкой «Внешние ресурсы / ручные действия: Да» разрешено
   пропускать именно так.
10. **Расхождение с документацией.** Если поведение продукта корректно с точки зрения
    пользователя, но расходится с формулировкой кейса (например, изменился текст сообщения),
    кейс получает `FAIL` с серьёзностью `S4`. В комментарии указывается, что именно
    расходится: нужно обновить кейс или продукт.
11. **Дефекты.** Каждый `FAIL` сопровождается описанием дефекта: шаги воспроизведения
    (минимальные), ожидаемый и фактический результат, артефакты. Если несколько кейсов падают
    из-за одной причины, оформляется один дефект со ссылками на все кейсы.

### Статусы

| Статус | Когда ставится |
|---|---|
| `PASS` | Все шаги выполнены, и фактический результат совпал с ожидаемым. |
| `FAIL` | Хотя бы один шаг не совпал с ожиданием, приложение упало или вышел тайм-аут. |
| `BLOCKED` | Кейс невозможно выполнить из-за окружения или предусловия (причина обязательна). |
| `SKIPPED` | Кейс сознательно исключён из прогона: не та архитектура, сокращённый прогон и т. п. Причина обязательна. |
| `NOT_RUN` | Кейс не начат, потому что прогон прерван. |

### Серьёзность дефектов

| Уровень | Описание |
|---|---|
| `S1` — критический | Авария, зависание, потеря или порча данных и настроек, невозможность открыть файл. |
| `S2` — высокий | Основная функция работает неправильно, обходного пути нет. |
| `S3` — средний | Функция работает неправильно, но есть обходной путь, или это краевой случай. |
| `S4` — низкий | Косметика, тексты, расхождение с документацией. |

## Формат отчёта

Агент создаёт папку `tests/regression/reports/<YYYY-MM-DD_HHMM>_<версия>/` с тремя элементами:

```text

├── report.md          # человекочитаемый отчёт (формат ниже)
├── results.json       # машиночитаемые результаты (схема ниже)
└── artifacts/
    └── RT-SRCH-001/
        ├── step-01.png
        └── clipboard-03.txt
```

- «Заблокированные и пропущенные»;
- «Результаты по кейсам» — все кейсы набора, включая `NOT_RUN`.

Пошаговые детали обязательны для каждого `FAIL` и `BLOCKED`. Для `PASS` их можно не приводить.

Вердикт определяется так:

- **ГОТОВ К РЕЛИЗУ** — нет `FAIL` в P1 и нет дефектов S1/S2;
- **ГОТОВ С ЗАМЕЧАНИЯМИ** — есть только дефекты S3/S4 или `FAIL` в P2/P3 без S1/S2;
- **НЕ ГОТОВ К РЕЛИЗУ** — все остальные случаи.

Если больше 10% кейсов P1 получили `BLOCKED`, вердикт сопровождается пометкой «неполный прогон».

## Утилиты

| Скрипт | Назначение |
|---|---|
| `tools/New-LargeLog.ps1 -Path <файл> -SizeMB <N>` | Большой лог формата Classic с маркерами `[L-FIRST]`, `[L-MID]`, `[L-ERR]` (каждая 1000-я строка) и `[L-LAST]`. Выводит путь, число строк и размер. |
| `tools/Start-LogAppender.ps1 -Path <файл> -Count <N> -IntervalMs <мс> [-Truncate] [-PartialLast]` | Дописывает строки `[G-NNN]` в открытый файл (FileShare.ReadWrite). Используется для проверки работы с изменяющимися файлами. |
| `tools/Lock-LogFile.ps1 -Path <файл> -Share None\|Read\|ReadWrite -Seconds <N>` | Держит файл открытым с заданным режимом совместного доступа. |
| `tools/Get-CallStackSample.ps1 -Path <файл>` | Лог с реальными кадрами стека `ntdll.dll` и `kernel32.dll` текущей машины, плюс `<файл>.expected.json` с ожидаемыми функциями. |
| `tools/generate_testdata.py` | Перегенерирует `testdata/` вместе с `EXPECTED.md` для сертификатов. |
| `tools/generate_cases.py` | Генерирует `cases/` и `COVERAGE.md`, проверяет полноту покрытия. |

## Сопровождение набора

- Новая функция или исправленный дефект: добавить требования `REQ-*` и кейс в нужный модуль
  `tools/casedata/*.py`, затем запустить генератор. Для дефекта — добавить его в `CLOSED_ISSUES`
  в `generate_cases.py`.
- Изменились тексты UI: обновить ожидания в `casedata` (английские строки берутся из
  `LogGrokX/Localization/Strings.resx`).
- Изменились данные: поправить `generate_testdata.py`, перегенерировать данные и сверить кейсы,
  которые на них ссылаются (поиск по ID записи, например `[S10]`).
