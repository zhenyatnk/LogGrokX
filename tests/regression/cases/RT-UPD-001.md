## Цель

Регрессии #27, #29, #36, #40.

## Проверяемые требования

- `REQ-UPD-01` — Режимы UpdateMode: disabled / check / install; проверка при первом запуске в новый календарный день и по часовому таймеру; без лимита GitHub API (#36, #40).
- `REQ-UPD-05` — Портативная сборка не обновляется сама — открывает страницу релиза; проверка через системный прокси с учётными данными Windows (#29).

## Предусловия

- Выполнена базовая подготовка окружения из [README](../README.md#подготовка-окружения) (конфигурация, чистые данные пользователя).
- Доступ к github.com; установленная предыдущая версия LogGrokX.

## Шаги

| № | Действие | Ожидаемый результат |
|---|---|---|
| 1 | Установить предыдущий релиз (например v1.7.4 setup, см. `gh release list -R zhenyatnk/LogGrokX`). Settings → View → Automatic updates = `Do not check for updates`. Удалить `last-update-check.settings`, перезапустить. | Автоматической проверки нет (файл не создан, индикатора нет). |
| 2 | Режим `Check for updates`, Save, перезапуск. | Проверка при запуске: диалог `Update available` для последней версии; создан `last-update-check.settings`. |
| 3 | `Later`, перезапустить в тот же день. | Повторного диалога нет (проверка раз в календарный день), индикатор `Update to {0}` сохраняется. |
| 4 | Изменить `last-update-check.settings` на вчерашнюю дату (или перевести часы), перезапустить. | Проверка выполняется снова (#36). |
| 5 | 10 перезапусков подряд с удалением файла проверки. | Нет ошибок `403 (rate limit exceeded)`: тег определяется через redirect `releases/latest` (#40). |
| 6 | Включить системный прокси с аутентификацией Windows (если доступен), повторить проверку. | Проверка проходит через прокси (#29); иначе шаг BLOCKED. |

## Критерии прохождения

- Фактический результат каждого шага совпадает с ожидаемым.
- Нет аварийного завершения, зависаний UI > 5 с и необработанных исключений в логе `%LOCALAPPDATA%\LogGrokX\`.
