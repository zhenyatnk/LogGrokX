# Регресс-тестирование LogGrokX

Скилл запускает ручной (UI) регресс-набор из `tests/regression` на Windows-стенде и
формирует отчёт. Подробные правила лежат в `tests/regression/README.md`. Этот файл задаёт
порядок работы и ссылается на разделы README, но не дублирует их.

## Входные параметры

Параметры берутся из запроса пользователя. Если параметр не указан, его значение определяется
так, как написано в таблице. Пользователя переспрашивают только тогда, когда тестируемую сборку
найти не удалось.

| Параметр | Если не указан |
|---|---|
| Тестируемая сборка (`LogGrokX.exe`) | Найти установленную: `%LOCALAPPDATA%\Programs\LogGrokX\`, `%ProgramFiles%\LogGrokX\`, затем `LogGrokX\bin\Release\**\LogGrokX.exe` в репозитории. Если найдено несколько, взять самую новую по `--version` и записать выбор в отчёт. |
| Вид сборки | Определить по расположению: каталог установки → `setup`, рядом `*.dll` .NET-рантайма → `self-contained`, сборка из репозитория → `локальная`, иначе `portable`. |
| Состав прогона | Все кейсы из `tests/regression/cases`. |
| Сеть | Проверить: `Test-NetConnection github.com -Port 443` и `Test-NetConnection msdl.microsoft.com -Port 443`. |
| Права администратора | Проверить: `([Security.Principal.WindowsPrincipal][Security.Principal.WindowsIdentity]::GetCurrent()).IsInRole('Administrators')`. |
| Предыдущая версия для `RT-UPD-*` | Нет. Кейсы, которым она нужна, получают `BLOCKED`. |

Состав прогона задаётся одним из способов:

| Запрос | Какие кейсы выполнять |
|---|---|
| полный регресс, без уточнений | все файлы `cases/RT-*.md` |
| `P1`, `P1+P2` | кейсы с указанными приоритетами (поле «Приоритет» в шапке кейса) |
| области, например `SRCH, SAV` | `cases/RT-SRCH-*.md`, `cases/RT-SAV-*.md` |
| список ID | только перечисленные кейсы |
| issue, например `#89` | кейсы из строки этого issue в разделе «Дефекты → кейсы» файла `tests/regression/COVERAGE.md` |
| стенд без сети и прав администратора | все, кроме кейсов с отметкой «Внешние ресурсы / ручные действия: Да» |

Если в составе прогона есть неизвестный ID или область, сообщить об этом в отчёте и
продолжить с остальными кейсами.

## Порядок работы

1. Прочитать `tests/regression/README.md` целиком. Обязательны разделы «Окружение»,
   «Подготовка окружения», «Правила выполнения для агента», «Формат отчёта».
2. Определить входные параметры по таблице выше. Вычислить `%RT%`, `%APP%`, `%DATA%`,
   `%LOGS%`, `%TEMP%`.
3. Создать каталог отчёта `tests/regression/reports/<YYYY-MM-DD_HHMM>_<версия>/` и
   подкаталог `artifacts/`. Сразу записать в `report.md` раздел «Окружение».
4. Выполнить «Подготовку окружения» из README, включая резервную копию
   `appsettings.yaml` и файлов из `%DATA%`.
5. Составить список кейсов и упорядочить его: `P1` → `P2` → `P3`, внутри приоритета по ID.
   `RT-UPD-*` и `RT-INS-*` поставить в конец.
6. Для каждого кейса:
   1. Прочитать `cases/<ID>.md` полностью, включая «Предусловия», «Краевые случаи и
      примечания» и «Очистку».
   2. Проверить предусловия и внешние ресурсы. Если их нет, поставить `BLOCKED` с причиной и
      перейти к следующему кейсу. Не пытаться обойти ограничение.
   3. Выполнить шаги по порядку. Каждый ожидаемый результат проверять буквально, а
      доказательства сохранять в `artifacts/<ID>/` по правилу «Доказательства».
   4. Поставить статус и серьёзность по README. Если кейс просит зафиксировать фактическое
      поведение, описать в отчёте, что наблюдалось.
   5. Выполнить «Очистку» кейса.
   6. Сразу дописать результат в `report.md` и `results.json`. Если прогон прервётся, уже
      полученные результаты должны сохраниться.
7. Если приложение упало или зависло, выполнить правило «Аварии», перезапустить приложение
   и продолжить со следующего кейса.
8. Восстановить резервную копию пользовательского состояния и закрыть приложение.
9. Дописать «Итог» и вердикт по правилу из README. Проверить, что `results.json`
   соответствует схеме, а у каждого кейса из списка есть статус. Невыполненные кейсы
   получают `NOT_RUN` с причиной.

## Ограничения

- Не менять код продукта, `tests/regression/cases`, `tests/regression/testdata` и
  `tests/regression/tools`. Если кейс кажется ошибочным, записать это в «Замечания» отчёта.
- Не создавать issue, не комментировать и не отправлять в GitHub ничего. Отчёт не коммитить:
  каталог `reports/` есть в `.gitignore`.
- Не выполнять действий вне тестового стенда и не устанавливать постороннее ПО.
  `RT-INS-*` и `RT-UPD-*` меняют установленную версию. Их выполнять только на отдельной
  машине или виртуальной машине, иначе ставить `BLOCKED` с причиной «не тестовый стенд».

## Итоговый ответ пользователю

Коротко, без пересказа отчёта:

- путь к каталогу отчёта;
- версия и вид сборки;
- вердикт `READY` / `READY_WITH_REMARKS` / `NOT_READY`;
- число кейсов по статусам `PASS` / `FAIL` / `BLOCKED` / `SKIPPED` / `NOT_RUN`;
- дефекты `S1`–`S2`: ID кейса и одна строка описания;
- причины `BLOCKED`, сгруппированные (например, «нет сети — 4 кейса»).
