# Регресс-тестирование LogGrokX

Скилл запускает ручной (UI) регресс-набор из `tests/regression` на Windows-стенде и
формирует отчёт. Подробные правила лежат в `tests/regression/README.md`. Этот файл задаёт
порядок работы и ссылается на разделы README, но не дублирует их.

## Входные параметры

Параметры берутся из запроса пользователя. Если параметр не указан, его значение определяется
так, как написано в таблице. Пользователя переспрашивают только тогда, когда тестируемую сборку
найти не удалось.

| Параметр | Если не указан |
|---|---|
| Тестируемая сборка (`LogGrokX.exe`) | Найти установленную: `%LOCALAPPDATA%\Programs\LogGrokX\`, `%ProgramFiles%\LogGrokX\`, затем `LogGrokX\bin\Release\**\LogGrokX.exe` в репозитории. Если найдено несколько, взять самую новую по `--version` и записать выбор в отчёт. |
| Вид сборки | Определить по расположению: каталог установки → `setup`, рядом `*.dll` .NET-рантайма → `self-contained`, сборка из репозитория → `локальная`, иначе `portable`. |
| Состав прогона | Все кейсы из `tests/regression/cases`. |
| Сеть | Проверить: `Test-NetConnection github.com -Port 443` и `Test-NetConnection msdl.microsoft.com -Port 443`. |
| Права администратора | Проверить: `([Security.Principal.WindowsPrincipal][Security.Principal.WindowsIdentity]::GetCurrent()).IsInRole('Administrators')`. |
| Предыдущая версия для `RT-UPD-*` | Нет. Кейсы, которым она нужна, получают `BLOCKED`. |

Состав прогона задаётся одним из способов:

| Запрос | Какие кейсы выполнять |
|---|---|
| полный регресс, без уточнений | все файлы `cases/RT-*.md` |
| `P1`, `P1+P2` | кейсы с указанными приоритетами (поле «Приоритет» в шапке кейса) |
| области, например `SRCH, SAV` | `cases/RT-SRCH-*.md`, `cases/RT-SAV-*.md` |
| список ID | только перечисленные кейсы |
| issue, например `#89` | кейсы из строки этого issue в разделе «Дефекты → кейсы» файла `tests/regression/COVERAGE.md` |
| стенд без сети и прав администратора | все, кроме кейсов с отметкой «Внешние ресурсы / ручные действия: Да» |

Если в составе прогона есть неизвестный ID или область, сообщить об этом в отчёте и
продолжить с остальными кейсами.

## Порядок работы

1. Прочитать `tests/regression/README.md` целиком. Обязательны разделы «Окружение»,
   «Подготовка окружения», «Правила выполнения для агента», «Формат отчёта».
2. Определить входные параметры по таблице выше. Вычислить `%RT%`, `%APP%`, `%DATA%`,
   `%LOGS%`, `%TEMP%`.
3. Создать каталог отчёта `tests/regression/reports/<YYYY-MM-DD_HHMM>_<версия>/` и
   подкаталог `artifacts/`. Сразу записать в `report.md` раздел «Окружение».
4. Выполнить «Подготовку окружения» из README, включая резервную копию
   `appsettings.yaml` и файлов из `%DATA%`.
5. Составить список кейсов и упорядочить его: `P1` → `P2` → `P3`, внутри приоритета по ID.
   `RT-UPD-*` и `RT-INS-*` поставить в конец.
6. Для каждого кейса:
   1. Прочитать `cases/<ID>.md` полностью, включая «Предусловия», «Краевые случаи и
      примечания» и «Очистку».
   2. Проверить предусловия и внешние ресурсы. Если их нет, поставить `BLOCKED` с причиной и
      перейти к следующему кейсу. Не пытаться обойти ограничение.
   3. Выполнить шаги по порядку. Каждый ожидаемый результат проверять буквально, а
      доказательства сохранять в `artifacts/<ID>/` по правилу «Доказательства».
   4. Поставить статус и серьёзность по README. Если кейс просит зафиксировать фактическое
      поведение, описать в отчёте, что наблюдалось.
   5. Выполнить «Очистку» кейса.
   6. Сразу дописать результат в `report.md` и `results.json`. Если прогон прервётся, уже
      полученные результаты должны сохраниться.
7. Если приложение упало или зависло, выполнить правило «Аварии», перезапустить приложение
   и продолжить со следующего кейса.
8. Восстановить резервную копию пользовательского состояния и закрыть приложение.
9. Дописать «Итог» и вердикт по правилу из README. Проверить, что `results.json`
   соответствует схеме, а у каждого кейса из списка есть статус. Невыполненные кейсы
   получают `NOT_RUN` с причиной.
10. Если пользователь явно попросил завести или обновить issues, выполнить раздел
    «GitHub issues по явному запросу». По умолчанию этот шаг не выполняется.

## Ограничения

- Не менять код продукта, `tests/regression/cases`, `tests/regression/testdata` и
  `tests/regression/tools`. Если кейс кажется ошибочным, записать это в «Замечания» отчёта.
- Без явного запроса пользователя не создавать issue, не комментировать и не отправлять в
  GitHub ничего. Отчёт не коммитить: каталог `reports/` есть в `.gitignore`.
- Не выполнять действий вне тестового стенда и не устанавливать постороннее ПО.
  `RT-INS-*` и `RT-UPD-*` меняют установленную версию. Их выполнять только на отдельной
  машине или виртуальной машине, иначе ставить `BLOCKED` с причиной «не тестовый стенд».

## GitHub issues по явному запросу

Этот раздел применяется только к существующему `results.json` и только после явного запроса
пользователя. Не требуется повторять регрессионный прогон, если отчёт уже проверен.

### Состав и оформление

1. Создать по одному issue на каждый уникальный дефект из `results.json → defects`; несколько
   FAIL одного дефекта объединяются. Не создавать issues для `BLOCKED`, `SKIPPED`, `NOT_RUN`.
2. Заголовок: `[Regression <версия>] <ID дефекта>: <краткое описание>`.
3. В описании указать версию и вид сборки, ОС, шаги, ожидаемый и фактический результат.
   Добавить ссылки на **все** связанные сценарии `tests/regression/cases/<ID>.md` через
   `blob/<commit>/...`. Использовать commit, который существует на GitHub и содержит эти файлы;
   не подставлять локальный или выдуманный hash и не пушить без разрешения.
4. Установить отдельные поля issue, а не labels:
   - `Type = Bug`;
   - `Priority = P1/P2/P3` по приоритету сценария; если сценариев несколько, взять наивысший
     (`P1` выше `P2`, `P2` выше `P3`);
   - `Severity = S1/S2/S3/S4` из дефекта в `results.json`.
5. Добавить только label `Regression <версия>`, если пользователь не просил другие labels.
   Не создавать labels `Bug`, `Priority: ...` или `Severity: ...` вместо соответствующих полей.
6. Русский текст и пути передавать через UTF-8 `--body-file` или JSON-файл, не через inline
   аргументы консоли. После записи прочитать issue через API и проверить отсутствие mojibake.

### Вложения и данные для воспроизведения

В каждый баг добавить скриншоты FAIL и комментарий `Исходные данные для воспроизведения`.
Нужны настоящие downloadable-ссылки `https://github.com/user-attachments/files/...`, а не
локальные пути, ссылки на локальный диск или содержимое файла только в code block. Команда
`gh issue comment` создаёт Markdown-комментарий, но не загружает файлы; загрузку выполнить
через форму GitHub. Один уже загруженный файл можно ссылать из нескольких issues.

Обязательно приложить входные файлы, используемые падающими шагами:

- логи из поля `Данные` связанных сценариев (`search.log`, `binary.log`, `hex.log` и т. п.);
- статические конфигурации из поля `Конфигурация`, если они нужны для воспроизведения
  (`appsettings.badprofile.yaml`, `appsettings.malformed.yaml`, legacy/inherit-конфигурации);
- JSON-файлы маппингов и другие входные данные из сценария;
- файл нулевой длины тоже является входными данными, если дефект относится к нему.

Не все артефакты прогона являются входными данными. Не прикладывать промежуточные файлы,
которые шаги создают сами и которые не нужны для начала воспроизведения: снимки
`appsettings-stepNN.yaml`, сохранённые копии YAML после действий в UI, временные выгрузки.
Например, для проверки `DetectHex=false` нужны исходные `binary.log` и `hex.log`, а полученный
в процессе `appsettings-step06.yaml` не нужен. Если такой лишний комментарий уже создан,
удалить его.

Диагностические доказательства не удалять: журнал приложения со stack trace, crash output,
замеры памяти/времени и содержимое буфера обмена, если они подтверждают фактический результат.
Их отличие от промежуточной конфигурации в том, что они фиксируют наблюдение, а не задают
начальные условия теста.

Большие генерируемые файлы (например, лог 1 ГБ) не прикладывать. Вместо этого дать постоянную
ссылку на генератор из репозитория и точную команду генерации. Если GitHub не поддерживает тип
файла генератора, сослаться на исходник в репозитории, а не замалчивать способ получения данных.
Для дефектов, воспроизводимых без входных файлов (например, только осмотром заголовка окна),
комментарий с данными не требуется.

### Проверка перед завершением

Проверить каждый созданный или изменённый issue через API и открытые ссылки:

- тип, Priority и Severity находятся в отдельных полях и совпадают с отчётом;
- labels соответствуют запросу, лишних `Priority:`/`Severity:` нет;
- русский текст, имена файлов и ссылки на сценарии не повреждены;
- есть скриншоты и все необходимые исходные файлы, нет временных сводных комментариев и
  промежуточных артефактов;
- каждая ссылка на вложение доступна. Нулевой файл может возвращать HTTP 416 на `HEAD`/`GET`
  из-за нулевого размера; это проверять отдельно и не считать признаком отсутствующего файла.

Скрипты и рабочие заметки для массового обновления хранить в `issue_work/` внутри каталога
отчёта. Не удалять их без запроса пользователя. В итоговом ответе дать ссылки на issues и
кратко перечислить добавленные данные и удалённые лишние артефакты.

## Итоговый ответ пользователю

Коротко, без пересказа отчёта:

- путь к каталогу отчёта;
- версия и вид сборки;
- вердикт `READY` / `READY_WITH_REMARKS` / `NOT_READY`;
- число кейсов по статусам `PASS` / `FAIL` / `BLOCKED` / `SKIPPED` / `NOT_RUN`;
- дефекты `S1`–`S2`: ID кейса и одна строка описания;
- причины `BLOCKED`, сгруппированные (например, «нет сети — 4 кейса»).
